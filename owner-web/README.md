# Chai And Tapri Owner Web — OW-01 / OW-05 / OW-06

The first owner web screen is served by the local sync API at `/owner/`. Start the backend as described in [`backend/README.md`](../backend/README.md), after applying its migrations to a dedicated development PostgreSQL database.

Sign in with the owner email/password and the shop/device IDs created by the Android Cloud Sync registration flow. The Android Cloud Sync screen displays those non-secret identifiers after registration/login. The bearer token is held only in page memory. The summary loads from authenticated, accepted server event records; it does not include unsynced Android records or the entity types still blocked by the synchronization contract.

This is an OW-01 prototype. It is not a public deployment or an authoritative financial ledger, and it must not be used as proof of shop profitability. The data scope and evidence labels are shown in the UI.

The Product performance section calls the owner-only `/v1/dashboard/products?shopId=<uuid>` endpoint. It reports delivered/returned quantities and item value by product from latest accepted order snapshots, along with accepted stock status. It does not include offline/blocked events, product catalogue display names/costs, profit, or trusted calendar-date filtering. Product units remain separate. OW-05 is partial and has not received browser visual review.

The Inventory snapshot section calls the owner-only `/v1/dashboard/inventory?shopId=<uuid>` endpoint. It shows latest accepted stock snapshots per product and up to 100 distinct accepted stock movement records. Known, unknown and unreported stock remain separate. Unit metadata is not yet in the accepted sync contract, so quantities are not added across product IDs. The view does not infer low-stock status, missing sales, waste, theft, reorder needs, or profit because catalogue units, reorder thresholds and costs are not yet available to this endpoint. OW-06 is implemented at API/UI-source level; database-backed endpoint integration and browser visual review remain pending.

The Sales Activity section calls the owner-only `/v1/dashboard/activity?shopId=<uuid>&days=7|30|90` endpoint. It groups accepted journal changes using the server's UTC receipt date and reconstructs prior order state before the displayed range. Delivered item value is a net state change, not profit or a complete sales ledger. Cash/UPI values are staff-declared, not provider-verified; pending UPI is attempts started during the range, not the current pending balance. Accepted expense projections include only ID, normalized category, paise amount, tender method, and declared status; notes and drawer links stay local. Expense records are counted once and remain staff-declared. Offline/blocked events and unsupported entities are absent. OW-02 API/UI source is implemented; PostgreSQL-backed integration and browser visual review remain pending. See [`OW-02 report`](../specs/OW-02-DAILY-SALES-ACTIVITY-REPORT.md) and [`CAT-052 expense projection report`](../specs/CAT-052-EXPENSE-PROJECTION-REPORT.md).

The **Export current report** action downloads a CSV snapshot of the currently displayed, last successfully loaded owner view (overview, products, inventory, activity, cashflow, profit readiness, or audit metadata). Export is disabled while a view is loading, invalidated before refresh, and cleared on sign-out. The CSV includes the visible scope and evidence/limitation text, labels the data source as server-accepted, timestamps the view, quotes cells, preserves Unicode, and neutralizes spreadsheet formula-leading text. It does not make another API request, export bearer credentials, include unsynced device records, or turn limited aggregates into a complete accounting report. Browser visual review remains pending. See [`OW-15 report export`](../specs/OW-15-OWNER-REPORT-CSV-EXPORT-REPORT-2026-11-23.md).

## Additional current owner views

The owner application also includes authenticated supplier balances (OW-07), customer balances (OW-08), recorded cashflow (OW-04), profit readiness (OW-03), and accepted event history (OW-12). OW-07 and OW-08 use privacy-minimized opaque identifiers and display only server-accepted, synchronized event projections. Recorded settlements are staff-declared, not provider-verified. These views do not constitute complete accounting, do not include unsynchronized local activity, and are not browser-visually qualified. See the corresponding CAT-052 and OW reports in specs/.

## OW-10 anonymous shift summary — 24 November 2026

The `/v1/dashboard/shifts` owner view reads accepted `staffShifts` projections. The Android outbox sends a stable opaque session UUID, session kind, device-clock start/end timestamps, and device-declared opening, expected, and counted cash. Operator and handover labels/notes remain local. The owner UI spells out that identities are not authenticated, timestamps and cash are not independently verified, and these records do not establish attendance or payroll. PostgreSQL integration and an API 37 Android-to-owner sync E2E pass for the synthetic scenario; authorized browser visual review remains pending. See [`OW-10 report`](../specs/OW-10-ANONYMOUS-SHIFT-SUMMARIES-REPORT-2026-11-24.md).

## OW-09 server memberships — 24 November 2026

The Staff access owner tab can create manager/cashier invitations, display the random one-time invite secret only in the creation response, list shop members and invitation states, change staff roles, revoke an invitation, remove a member (which revokes their server sessions), and read append-only membership-event metadata. The invite secret is stored only as a SHA-256 hash and expires after 24 hours. Invitation and membership/audit reads and writes have forced shop-scoped PostgreSQL RLS. Email ownership is not verified. The public invite-acceptance API creates or reuses an account only after one-time token validation (existing accounts must prove their password), registers the invited device and creates a shop session. There is no Android invitation-acceptance UI or email/SMS delivery yet. Manager/cashier roles do not currently impose per-command permissions on synced business events, and do not link to device-local PIN identities; do not treat this as full staff authorization or actor attribution. Backend route/UI-source and isolated PostgreSQL tests pass; no browser visual review was performed. See [`OW-09 report`](../specs/OW-09-STAFF-MEMBERSHIP-REPORT-2026-11-24.md).
