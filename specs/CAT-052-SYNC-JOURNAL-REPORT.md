# CAT-052 — Authenticated Sync Foundation Report

**Date:** 30 October 2026  
**Status:** Local backend prototype and limited Android outbox payload foundation implemented and tested; authenticated Android synchronization not implemented.

## Implemented

- PostgreSQL schema for businesses, shops, users, shop roles, enrolled devices, hashed sessions, login-failure tracking, sync events and revision conflicts.
- Password hashing with Node `scrypt`; opaque random session tokens are returned once and only SHA-256 token hashes are stored. Sessions expire and can be revoked on logout. Login failures are counted and locked for a limited period.
- Authenticated shop and device checks on sync requests. Event batches validate IDs, tenant scope, schema version, payload shape and bounded request size.
- Server-side shop row locking and monotonically increasing revisions. An exact event retry is acknowledged as duplicate; changed content under a reused event/command ID is rejected; a stale base revision is recorded as a conflict.
- Migration `002_command_key_text.sql` adapts the server idempotency key to existing native command IDs, which may be prefixed strings rather than UUIDs. An upgrade fixture with a preexisting UUID event was migrated and its command ID preserved as text.
- Local Node HTTP API and migration runner. The development server binds to loopback by default.

## Android outbox payload foundation — 30 October 2026

SQLite schema v18 adds `payload_version`, `payload_json`, `blocked_reason` and `base_revision`. The additive v17→v18 migration preserves historical outbox rows, assigns UUID event IDs distinct from command IDs, and marks rows with unavailable historical payloads `blocked_contract` rather than synthesizing replay data. For supported mutations, `SyncOutboxPayloadEncoder` creates a compact allow-listed `projection_delta.v1` payload from before/after state for order changes, stock balances/movements and payment entries without customer identity. Customer-linked credit, repayment, and payment changes are atomically marked `customer_identity_contract_pending`: current account IDs are operator-defined strings and may be a name or phone number, so they are not safe for future upload until an opaque identity and consent contract exists. Free-form audit text, cancellation reasons, product display names and unrelated business data are excluded. Other mutations without a contract are also recorded as `blocked_contract`; blocked rows must not be uploaded.

The focused v16→v18 migration, new sale/outbox/idempotency case, and shop-setup maintenance-barrier case passed on the API 37 emulator. A complete `connectedDebugAndroidTest` run passed 44/44 (XML exit code 0); Kotlin JVM 33/33; Node 49/49; `assembleDebug`, `assembleDebugAndroidTest` and `lintDebug` passed, with 0 lint errors and 113 warnings. Test artifacts are under `android/app/build/outputs/androidTest-results/connected/debug/` and `android/app/build/test-results/testDebugUnitTest/`.

This remains a payload foundation, not delivery readiness. `base_revision` is currently null because the app has no server cursor. The backend expects a `business.command.v1` envelope and authoritative revision; Android has not mapped projection deltas into that envelope, enrolled accounts/devices, protected auth tokens, added a WorkManager uploader, persisted acknowledgements or presented conflicts. A local outbox row marked `pending` must not be interpreted as server accepted. Coverage proves migration, selected payload contents and customer-ID blocking, not complete entity parity or authenticated sync.

## Server-side payload contract validation — 30 October 2026

The backend now accepts only the `projection_delta.v1` payload shape for schema version 1. It rejects unknown fields/kinds, malformed order and line structures, non-integer monetary/quantity fields, invalid states, oversized arrays, negative stock and empty deltas. Customer-linked credit/repayment arrays and payment entries with a customer ID are rejected until the identity contract is privacy-reviewed. The backend still journals validated payloads; it does not apply these deltas to authoritative server financial projections. A synthetic isolated PostgreSQL 17 run passed all 9 backend tests (5 contract tests and 4 service/HTTP integration tests) through the non-superuser runtime role. The ephemeral server was stopped afterward. No Android-to-server integration was tested.

## Android envelope mapping contract — 30 October 2026

Added a pure request-envelope mapper for the current backend contract. It binds each event to the configured business/shop/device identity, preserves the event and command IDs and validated `projection_delta.v1` payload, and emits `business.command.v1` request envelopes. For a batch of new events, it advances `baseRevision` by one per event to match the backend's sequential revision increments; overflow, non-canonical UUIDs, invalid IDs/versions, duplicate IDs, malformed payloads, unsupported kinds and invalid batch sizes are rejected. The Android instrumentation test parses the serialized request with platform JSON and checks the shop scope, envelope fields, payload and revision progression (`7`, `8`). JVM coverage checks pre-serialization validation.

## Superseding continuation — CAT-052 durable outbox outcome journal — 30 October 2026

Implemented encrypted SQLite schema v20 with a `server_revision` on sync outbox rows and persistence APIs to read sendable pending events, read the current acknowledged server revision, and record accepted/duplicate/conflict outcomes. Event acknowledgement is atomic with row status and the cursor update; repeated identical acknowledgements are idempotent; conflicting or altered replays are rejected. A conflict records the server revision and blocks later queued events from being returned. The follow-up guard now rejects an acknowledgement for any event other than the earliest currently eligible event, preventing an out-of-order response from advancing the cursor past earlier work. Historical non-sendable/blocked rows remain excluded. Added an API 37 instrumentation scenario that downgrades a synthetic database to v19, verifies the additive v19→v20 migration preserves queued events, tests out-of-order rejection, accepted/duplicate outcomes, a conflict, durable statuses and cursor blocking. The focused test passed 1/1 after the final guard change.
