This is a local development service implemented with Node.js and PostgreSQL. It provides owner/shop/device enrollment, password authentication, revocable expiring sessions, shop-scoped access checks, and an immutable receipt journal for versioned business command envelopes.

## Run locally

Use a dedicated development PostgreSQL database. Do not point this service at the laptop's unrelated PostgreSQL service or production data.

```powershell
$env:DATABASE_URL = 'postgres://USER:PASSWORD@127.0.0.1:5432/DB'
npm.cmd install
npm.cmd run migrate
npm.cmd test
npm.cmd start
```

For a deployed runtime identity, apply all numbered migrations first, then apply `ops/runtime-grants.sql` as the database administrator with the actual database name (`psql -v database_name=APP_DB -f ops/runtime-grants.sql`), then create a LOGIN role using the organization's secret-management process and grant it membership in `chai_tapri_api`. The SQL file intentionally contains no login secret. The API role can perform the rows needed for registration, login, session revocation, invitation/member administration and sync; it cannot delete immutable event or staff-audit history, create schema objects, or own RLS tables.

The API binds to `127.0.0.1:8787` by default. Routes include `POST /v1/register`, `POST /v1/login`, `POST /v1/logout`, `POST /v1/sync/events`; owner-only staff routes `GET|POST /v1/staff/invitations`, `DELETE /v1/staff/invitations/:id?shopId=<uuid>`, `GET /v1/staff/members?shopId=<uuid>`, `PATCH|DELETE /v1/staff/members/:userId`, and `GET /v1/staff/audit?shopId=<uuid>`; public one-time `POST /v1/staff/accept-invitation`; and owner-only dashboard routes `/v1/dashboard/overview`, `/v1/dashboard/insights`, `/v1/dashboard/products`, `/v1/dashboard/inventory`, `/v1/dashboard/suppliers`, `/v1/dashboard/customers`, `/v1/dashboard/shifts`, `/v1/dashboard/activity?shopId=<uuid>&days=7|30|90`, `/v1/dashboard/cashflow?shopId=<uuid>&days=7|30|90`, and `/v1/dashboard/profit-readiness?shopId=<uuid>&days=7|30|90`. Invitations are limited to manager/cashier roles, expire after 24 hours, and return a random one-time secret only at creation; only its SHA-256 hash is stored. Email ownership is unverified. Membership and invitation/audit tables use forced shop-scoped RLS. The staff audit is append-only metadata for membership/invitation changes, not a complete business audit. Migration 004 enforces membership-derived role limits for supported synced business projections; Android local staff PIN accounts can be linked by the CAT-052 Staff Cloud Access screen after accepting a one-time manager/cashier invitation; role equality is checked before the server session is stored in that local actor encrypted vault. The Staff Cloud Access Android screen's invitation acceptance, manual actor-scoped sale sync and disconnect flow passed a focused API 37 emulator E2E against a synthetic isolated PostgreSQL 17 backend on 24 November 2026; this is not a full Android regression or production sync qualification (see `../specs/CAT-052-STAFF-INVITATION-ANDROID-POSTGRES-E2E-REPORT-2026-11-24.md`). Supplier balances are a privacy-minimized accepted-event summary keyed by opaque sync IDs; settlements are staff-declared, not bank-verified. Shift summaries use opaque session IDs and omit operator labels/notes; timestamps and cash figures are client-declared, and the view is not authenticated attendance or payroll. Cashflow is a partial accepted-record movement summary, not complete accounting; profit readiness reports known inputs and keeps profit unavailable when cost coverage is absent. The local owner dashboard is served at `/owner/`; `/owner` redirects to it. Registration is currently an open development onboarding endpoint. A real deployment requires TLS, registration abuse controls, a managed secret store, operational monitoring, backup/recovery, stronger identity/MFA policy and a reviewed production authorization model.

## Sync contract boundary

### Membership-derived sync authorization (migration 004)

The sync endpoint derives the writer role from the authenticated shop membership; it ignores any client-supplied role. Owners and managers may submit the current allow-listed projection families. Cashiers may submit orders, collections, opaque customer credit/repayment records and shift summaries, but not expenses, purchasing, supplier payments/returns, refunds, order cancellation/void, positive/manual inventory movements, or stock snapshots that do not reconcile exactly to prior server stock and delivered-quantity changes. Cashier collection/credit totals must match the corresponding order balance deltas. Authenticated Android sync now downloads the latest accepted catalogue snapshot, but offline sales still use the local confirmed catalogue and this service does not enforce that a submitted sale used a current server catalogue price. These checks do not enforce local actions while offline or link Android PIN identities to cloud accounts.

Each newly accepted event records the authenticated submitting user ID and role. The owner event-history view may show that account's display name. This is submitter attribution only; it does not prove who performed an offline action on a shared device. Existing journal rows remain unattributed. Managers can submit current business projections but remain denied owner dashboard and membership-administration endpoints. Cashiers are denied those endpoints as well.

`business.command.v1` envelopes contain event, command, business, shop and device IDs, schema version, base server revision and a JSON payload. Schema version 1 accepts the strict `projection_delta.v1` allow-list: bounded arrays, integer paise/quantities and known states are required. Optional v1 additions include `expenses`, `estimatedUnitCostPaise` on order lines, privacy-minimized `purchaseReceipts`, `supplierPayments`, `purchaseReturns`, and `staffShifts` arrays. Procurement payloads use persisted opaque UUIDs and only totals/method/status/receipt linkage; supplier names, phones, invoice references, item lines, notes and drawer/session links are excluded. Shift projections contain a stable opaque ID, session kind, device-clock timestamps and declared cash totals; staff/handover labels and notes stay local. The server rejects changes to closed sessions. Returns are validated against accepted receipt identity, supplier identity and remaining receipt value; procurement event IDs cannot be replayed under a new envelope. Customer-linked credit and repayment records use opaque UUID identities under the current sync contract. The service records accepted envelopes, recognizes exact retries, rejects reused IDs with altered contents and records stale-revision conflicts. Role-scoped sync restrictions and submitter attribution are described below. It does not execute a command against authoritative financial projections, resolve conflicts, or promise exactly-once delivery. Clients must retain their local outbox entries until they receive and persist an acknowledgement.

Android persists an encrypted sync outbox and server revision/outcome journal. Its minimized projection supports selected orders (including optional line cost estimates), stock movements, payment entries, opaque customer credit/repayments, expenses, supplier receipts/payments/returns, privacy-minimized shift summaries and catalogue changes. Unsupported entities remain blocked; expense notes and drawer/session links are omitted. Owner and staff sync paths push through the HTTPS transport and then fetch the membership-authorized catalogue snapshot. A synthetic Android API 37 emulator-to-PostgreSQL HTTPS drill, including a simulated lost acknowledgment, idempotent retry, outbox recovery, owner projection and catalogue pull into SQLCipher, passed on 26 November 2026; this is local prototype qualification, not a deployed or production sync service. Server journal acceptance is not an authoritative business projection, and owner reports include only accepted events.

Database migration `001_core.sql` enables row-level security for event and conflict tables. API queries also bind the authenticated shop explicitly. Tests have exercised cross-shop read/write isolation as the least-privilege non-superuser role created from `ops/runtime-grants.sql`; they also verify that this role cannot delete immutable sync events. The grant set still needs independent review before deployment.

The current isolated PostgreSQL 17 test run passed 9/9: five payload-contract tests plus four authenticated service/HTTP integration tests. Tests use only synthetic records and a temporary local cluster; the cluster was stopped after the run.
